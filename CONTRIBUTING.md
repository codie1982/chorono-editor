# Contributing to Chorono

Contributions to the editor, MCP bridge, CLI, agent skills, documentation and examples are welcome. Please follow the [Code of Conduct](CODE_OF_CONDUCT.md).

## Choose the right place

- Search [existing issues](https://github.com/codie1982/chorono-editor/issues) before reporting a problem or proposing a feature.
- Use the [bug report](https://github.com/codie1982/chorono-editor/issues/new?template=bug_report.yml) for reproducible failures, or the [feature request](https://github.com/codie1982/chorono-editor/issues/new?template=feature_request.yml) to explain a use case and proposed improvement.
- Use [first animation feedback](https://github.com/codie1982/chorono-editor/issues/new?template=first-animation-feedback.yml) for installation, connection, editing and save/reopen experiences, including blocked attempts.
- Ask questions and share animations in [Discussions](https://github.com/codie1982/chorono-editor/discussions). Discuss larger architectural changes before implementing them.
- Report suspected vulnerabilities privately using [SECURITY.md](SECURITY.md).

## Prepare a development checkout

Use Git, Node.js 22.x (22.12 or later), npm and a modern browser. CI uses Node.js 22 on Ubuntu; report other platforms you actually test.

Fork the repository if you do not have write access, then clone your fork. From the checkout:

```sh
git switch -c codex/describe-your-change
npm ci
npm run cli:build
```

Use a focused feature branch and open a pull request targeting `main`. Direct pushes, force pushes and deletion of `main` are blocked.

For the visual editor, run `npm run dev` and open the printed URL. For MCP development, follow the [installation and connection guide](docs/en/installation.md). A running HTTP server alone does not mean the editor tab is connected; pair it through **MCP → Connect this editor** and check `npm run chorono -- doctor`.

Stop the Next.js dev or production server for this checkout before installing dependencies or building. Concurrent builds and servers share `.next/` and can corrupt it.

## Make a focused change

- Read [AGENTS.md](AGENTS.md) and the instructions in any directory you change.
- Follow the existing architecture and code style. Keep unrelated changes out of the PR.
- Add regression coverage for behavior changes where useful. Explain when a change needs manual validation instead.
- For visible editor changes, check the actual UI and include a screenshot or short recording with reproduction steps.
- For animation changes, check representative preview frames, editable layers/keyframes and the save/reopen workflow. State the browser, operating system and agent client you tested.
- For MCP API or workflow changes, update the matching documentation and canonical `skills/` instructions. `packages/cli/skills/` is generated by `npm run cli:build`; do not edit it directly.

Keep `.env` files, `.chorono/` credentials, client configuration backups and private animation projects out of commits. Remove tokens, API keys and private assets from logs, screenshots and sample projects.

## Validate the change

With the server stopped, run the same checks as CI:

```sh
npm run cli:build
npm test
npm run cli:test
npm run mcp:build
npm run build
git diff --check
```

`npm ci` performs the clean dependency install in CI. If you intentionally change dependencies, update `package-lock.json` and verify that a clean `npm ci` succeeds; do not replace it with `npm install` in the workflow to hide lockfile errors.

For CLI installer or packaging changes, also run `npm run cli:pack`, inspect the resulting tarball and test installation from it. See the [distribution guide](docs/tr/skills.md). The root npm package is private; package publication is a separate maintainer task, not part of a normal contribution.

Documentation-only changes should have working links, valid template YAML where relevant and no whitespace errors. CI still runs for these PRs. List checks you actually performed and note anything you could not test.

## Open a pull request

Explain the problem, resulting behavior and validation in the [PR template](.github/PULL_REQUEST_TEMPLATE.md). Link the relevant issue when one exists and include a minimal example for animation or MCP problems.

The required **Tests and builds** check must pass against the latest `main` before merge. Resolve review conversations and rerun relevant checks when you update the PR. Do not claim platform compatibility or test results that you have not verified.

Contributions are made under the repository's [MIT license](LICENSE). Submit only code, media and examples that you have permission to share.
